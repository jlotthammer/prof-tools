# C++ / Rust instrumentation and correctness checklist

## Native build identity
- Record `git rev-parse HEAD`, compiler and runtime versions, optimization flags, target/ISA, `-march`, LTO, sanitizer and allocator configuration, library ABIs, binary checksums, build IDs and symbol files. Debug symbols (`-g`) are compatible with optimized builds; `-O0` is not representative.
- Frame-pointer unwinding may fail if binary and shared libraries omit frame pointers; use `--call-graph dwarf` where supported. DWARF stacks increase sampling/recording cost. Missing stacks invalidate caller-level diagnoses.
- On Linux `perf record --call-graph fp|dwarf|lbr` availability depends on platform and hardware (LBR x86-specific). Use no `sudo` and do not change `perf_event_paranoid`; report unavailable capabilities. Alternative: `samply` with approved permissions or function-level scopes.
- `perf stat` hardware events may be unsupported, unprivileged, multiplexed, or scaled. Compare cycles/instructions only in matched event scopes; avoid inventing bandwidth from cache misses alone.

## Cross-language calls
- `pybind11::gil_scoped_release`, PyO3 `Python::detach` / current API and Cython `nogil` are not safe substitutes for proving Python-object accesses are absent. Check library APIs against installed versions.
- Rust FFI unsafe code and C++ native kernels need boundary tests (shape/stride/ownership/lifetime/races, integer overflow and precision). Avoid transferring mutable buffers across threads unless synchronized.
- Distinguish code generated by Numba/JAX/TorchInductor from hand-coded native binaries; symbols and compiler cache paths are often ephemeral. Retain exact artifacts and dispatch decisions.

## Native hot path analysis
1. Which *function and callers* dominate samples? Was the sample time on-CPU or wall-time?
2. Is it limited by algorithmic work, data bandwidth, latency/cache misses, branch misprediction, instruction throughput, vectorization, synchronization, kernel entry or allocation?
3. What is the critical path and theoretical speedup bound for the specific input distribution? Sample percentage is not automatically an upper bound for end-to-end speedup in a multi-threaded application.
4. What existing SIMD/BLAS/vector library is faster and more portable than a specialized implementation?
5. Measure change unprofiled, with all code paths and accuracy validated, then profile anew if accepted.
