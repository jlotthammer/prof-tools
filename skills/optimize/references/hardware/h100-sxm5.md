# NVIDIA H100 SXM5 (GH100 / Hopper) — engineering reference

**Exact SKU only**: H100 SXM5, not PCIe, H100 NVL, H200, H800 or MIG partitions. Architectural and product facts below are vendor facts unless marked *derived*, *conditional* or *reported*. Verify the actual GPU with `nvidia-smi` and CUDA device properties; virtualization/MIG may reduce exposed resources.

## Die, execution and clocks
- GH100 full die has 144 SMs and 60 MB physical L2. H100 SXM5 enables **132 SMs**, 8 GPCs and 66 TPCs; **50 MB L2**.
- Per SM: 128 FP32 lanes, 64 FP64 lanes, 64 INT32 lanes, four 4th-gen Tensor Core instances in four subpartitions. Warp = 32 threads; warpgroup = 4 warps/128 threads.
- Advertised maximum boost clock 1,980 MHz (clock varies by implementation/power/temperature). Max board power up to 700 W. Interconnect: NVLink 4 18 links, advertised 900 GB/s **aggregate bidirectional**; PCIe Gen5 x16 host connectivity. Up to seven MIG instances, which must be treated as distinct devices and throughput models.
- `sm_90`: architectural CUDA 9.0 target. `sm_90a`: Hopper architecture-specific WGMMA/`setmaxnreg` features. These are not forward-portable architectures. Compile, identify and validate the actual target before predicting tensor throughput.

## Dense vendor throughput and peak assumptions
All values here are **dense** (sparse-product figures halved). NVIDIA's public H100 product page lists **sparse** tensor peaks of TF32 989, BF16/FP16 1,979, FP8 3,958 TFLOP/s for SXM. Approximate dense peaks (using published rounded vendor figures):

| Type | Dense vendor peak | Nominal operations/SM/clock |
|---|---:|---:|
| FP64 vector | 34 TFLOP/s | 128 FLOP |
| FP64 tensor | 67 TFLOP/s | 256 FLOP |
| FP32 vector | 67 TFLOP/s | 256 FLOP |
| TF32 tensor | 494.5 TFLOP/s | 2048 FLOP |
| BF16/FP16 tensor | 989.5 TFLOP/s | 4096 FLOP |
| FP8 tensor | 1979 TFLOP/s | 8192 FLOP |
| INT8 tensor | 1979 TOP/s | 8192 OP |

The BF16/FP16 989.4 TFLOP/s figure in the supplied reference is the same dense peak to vendor rounding precision. **Do not** treat all rows as achievable at the same clock: 132 × 4096 × 1.98 GHz would exceed the listed BF16 dense peak. The tensor rows imply roughly 1.83 GHz, while the FP32/FP64 vector row at 132 SM aligns with ≈1.98 GHz. Use sustained measured clocks when modeling.

## Memory hierarchy and residency
| Layer | Hardware | Operational implications |
|---|---|---|
| Registers | 65,536 × 32-bit registers = 256 KiB/SM; up to 255/thread allocation rule | WGMMA accumulator and persistent live-range pressure constrain occupancy |
| Shared/L1 | 256 KiB unified, selectable shared memory carveout up to 228 KiB/SM; **227 KiB max per block** with opt-in | TMA staging, swizzles, barriers and epilogue scratch consume common budget |
| Banks | 32 × 4 B | Check NCU bank conflicts and operand layout rather than assuming nominal coalescing |
| L2 | 50 MB effective | Check L2 hit/sector traffic, cache residency and cross-partition effects; physical split is secondary-source detail |
| HBM3 | 80 GB, 3.35 TB/s nominal peak | Measure bandwidth, ECC, occupied HBM and allocation peaks |
| Residency | up to 64 warps/SM; 32 blocks/SM; 1,024 threads/block | Register/smem limits generally bite before maximum block count |
| Block cluster | 8-CTA portable; larger up to 16 where nonportable opt-in supported | Clusters co-scheduled within a GPC; size interacts with grid tails |

Static shared memory has portability constraints; large dynamic allocations require explicit opt-in. See Hopper tuning guide before relying on a 227 KiB kernel.

## Hopper-specific kernel mechanisms
### Tensor Memory Accelerator
`cp.async.bulk.tensor` uses a host-created tensor-map descriptor (`cuTensorMapEncodeTiled`), bulk multidimensional tensor transfers, OOB fill, and `mbarrier` completion. Shared memory 32/64/128-byte swizzles constrain proper operand layouts. Cluster TMA multicast can amortize loading the same operand across neighboring CTAs. `cp.async` per-thread path remains available.

### WGMMA and warp-specialized pipelines
`wgmma.mma_async` is issued by one 128-thread warpgroup. Core tile is `m64nNkK`, with M fixed 64. BF16/FP16 K=16, TF32 K=8, FP8 and integer K=32; N generally multiples of 8 up to 256 subject to per-type restrictions. A can be register/shared, B shared; accumulators FP32 generally in registers. `wgmma.fence` → `mma_async` → `commit_group` → `wait_group` is the basic dependency sequence; production kernels must use the documented async pipeline synchronization rules.

- BF16/FP16 allow both shared-memory operand transpose layouts, while TF32/FP8 have K-major constraints; transforming attention V can require a layout conversion.
- **Register model:** an FP32 accumulator with BM×BN elements held by one warpgroup needs `(BM×BN)/128` registers/thread if evenly distributed; e.g. 64×256 → 128 registers/thread, before all other live registers.
- Producer warpgroup performs TMA, consumer warpgroups compute. `setmaxnreg` redistributes register allowances dynamically; values are multiples of 8 in the architectural range 24..256 and require architecture-specific code.
- Warpgroup MMA vs `mma.sync` is **not** a universal pass/fail for every kernel: small/ragged shapes or specialized kernels may perform better with other instructions. Confirm actual SASS and measured latency.
- Distributed shared memory (DSMEM) permits CTAs within a cluster to access shared memory and synchronize; no analogue on MI300A.

### Numerics
FP8 on H100 uses OCP E4M3 (finite max 448) and E5M2 (max 57,344). Long reduction chains, alignment and accumulation can affect error. The DeepSeek-V3 report describes a Hopper FP8 GEMM technique periodically promoting partial sums to FP32; it is evidence for an implementation-specific numerical concern, **not** a guarantee about all H100 FP8 operations. Verify accumulation, rounding and numeric quality in the actual kernel and library version. Tensor-core structured sparsity is 2:4 and changes both payload validity and mathematical work.

## Derived idealizations (not measurements)
- `ridge_FP64_tensor = 67 / 3.35 ≈ 20.0 FLOP/B`
- `ridge_TF32 = 494.5 / 3.35 ≈ 147.6 FLOP/B`
- `ridge_BF16 = 989.5 / 3.35 ≈ 295.4 FLOP/B`
- `ridge_FP8 = 1979 / 3.35 ≈ 590.7 FLOP/B`
- Square BF16 ideal GEMM `n ≈ 3×295.4 ≈ 886` meets peak HBM roofline. Small GEMMs, masks, cache reuse, launch overhead and tensor-core utilization invalidate naive crossover predictions.
- BF16 weight-stream decode crossover batch ≈ 295 under unrealistically perfect reuse and no auxiliary memory traffic.
- Aggregate shared memory at max carveout ≈ 132×228 KiB = 29.4 MiB; aggregate register storage 132×256 KiB = 33 MiB. These are **distributed** capacities, not a contiguous cache.
- A BF16 128×256×64 tile requires `(128+256)×64×2 = 48 KiB` operand stage; four stages need 192 KiB before barriers/epilogue and can potentially fit under 227 KiB.

## Optimization playbook (hypotheses, not mandates)
1. Confirm real GEMM shape/dtype/layout and whether cuBLASLt, PyTorch compiler, Triton or CUTLASS already provides best dispatch; benchmark the incumbent.
2. For **sufficiently large** dense GEMM/attention: consider CuTe/CUTLASS TMA→WGMMA pipelining, 128×128 or 128×256 and BK≈64 in BF16. Stage counts determined by register and shared-memory allocation, not solely the tile formula.
3. Use cluster multicast only when shared operand reuse outweighs scheduling/tail cost. Profile multiple batch and sequence lengths.
4. Persistent grids can reduce wave tails, but `132 CTAs` is not universally ideal: actual residency, tiles, cluster sizes, and long-tail imbalance control optimal scheduling.
5. For short sequence/attention, reductions, sampling and normalization, optimize launch count and CPU gaps **before** assuming a tensor-core throughput ceiling.
6. Validate numerical parity (forward, backward, updates) and remeasure in the full training step without profiling.

## On-device verification (read-only)
```bash
nvidia-smi -q
nvidia-smi topo -m
nvidia-smi --query-gpu=name,uuid,compute_cap,clocks.sm,clocks.mem,power.limit,memory.total --format=csv
nsys --version
ncu --version
```
Use `cudaGetDeviceProperties` (or PyTorch `torch.cuda.get_device_properties`) for SM count, per-block shared memory opt-in, per-SM shared memory, L2 size and compute capability. Check actual NUMA/NVLink topology. NCU: `SpeedOfLight`, `MemoryWorkloadAnalysis`, `LaunchStats`, `Occupancy`, `SchedulerStats`, roofline; NSYS for overlap and launch gaps. On shared nodes, do not change clocks or collect privileged counters without authorization.
