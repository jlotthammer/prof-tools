# AMD Instinct MI300A (CDNA 3 APU) — engineering reference

**Exact SKU only:** MI300A APU, `gfx942`, not MI300X, MI325X, MI350, or arbitrary ROCm device. MI300A is a **CPU+GPU APU sharing physical HBM**; its memory and programming behavior must not be inferred from discrete accelerator examples. Partition/driver/XNACK/firmware can change what a process sees. Verify before optimizing.

## Package and connectivity
- Six XCD GPU chiplets, 38 enabled CUs per XCD (40 physical) = **228 CUs**, 912 matrix cores and 14,592 stream processors. Three Zen 4 CCDs × 8 cores = **24 CPU cores** plus four IODs. The APU contains 13 chiplets in total.
- Nominal peak GPU engine clock 2.1 GHz. TDP 550 W nominal or up to 760 W for qualified liquid cooling system. Thermal power envelope is platform dependent.
- Eight HBM3 stacks, **128 GB**, 8192-bit, theoretical **5.3 TB/s** aggregate shared between CPU and GPU. **256 MB Infinity Cache** (memory-side, not a normal CUDA L2 analogue).
- Eight x16 Infinity Fabric capable links (four dedicated + four flexible PCIe Gen5/IF) rated at 128 GB/s each under the cited vendor conditions. Do NOT use sums of these link figures as measured point-to-point or collective throughput. A four-APU El Capitan node may wire two links between each pair; discover actual topology.
- Compile `gfx942`; whether `xnack+` / `xnack-` is supported/active affects system-allocator access and faulting. `gfx942` alone does not prove XNACK.

## Nominal dense vendor performance
| Type | Dense vendor peak | Per CU/clock, nominal |
|---|---:|---:|
| FP64 vector | 61.3 TFLOP/s | 128 FLOP |
| FP64 matrix | 122.6 TFLOP/s | 256 FLOP |
| FP32 vector / matrix | 122.6 TFLOP/s | 256 FLOP |
| TF32 (`xf32`) matrix | 490.3 TFLOP/s | 1024 FLOP |
| BF16 / FP16 matrix | 980.6 TFLOP/s | 2048 FLOP |
| FP8 (`fnuz`) matrix | 1961.2 TFLOP/s | 4096 FLOP |
| INT8 matrix | 1961.2 TOP/s | 4096 OP |

Values correspond to ~228 CUs × per-CU throughput × 2.1 GHz; AMD reports 2× for supported structured-sparse forms. Integer units are operations, not FLOP. Nominal peak is not achieved throughput, especially under shared CPU/GPU HBM use.

## Memory hierarchy and residency
| Component | Amount and design | Diagnostic consequences |
|---|---|---|
| VGPR/AccVGPR | ~512 KiB vector register capacity/CU, about 128 KiB per SIMD; architectural GPR split constraints | Register allocation and accumulation pressure govern active waves |
| SGPR | ~12.5 KiB/CU; per-wave allocation granularity | Scalar spills and scalar-memory traffic |
| LDS | **64 KiB/CU**, banked 32×4 B, workgroup allocation in blocks | At most 2×32 KiB double-buffered tiles before epilogue scratch; spills invalidate estimate |
| L1 vector | 32 KiB/CU | High-value locality for small repeatedly-used operands |
| Scalar cache / I-cache | about 16 KiB / 64 KiB shared between pairs of CUs | Strong control-flow/dispatch dependence |
| L2 | **4 MB per XCD** = 24 MB total, **not a single shared 24 MB L2** | XCD locality matters for repeated tiled accesses |
| Infinity Cache (MALL) | 256 MB memory-side cache | Do not conflate cache hit rates with HBM bandwidth; coherency details are revision-specific |
| HBM3 | 128 GB shared physical HBM, 5.3 TB/s nominal | CPU placement, page size, NUMA, fabric and XNACK affect effective bandwidth |
| Execution | wave64 only, 4 SIMDs/CU, max 8 waves/SIMD; up to 1024 workitems/group | Workgroup may have at most 16 waves, with occupancy subject to VGPR+LDS limits |

A rough register upper bound for waves/SIMD is `min(8, floor(512 / allocated_registers_per_lane))` for the relevant SIMD, **subject to compiler allocation granularity and other restrictions**. Per-wave VGPR vs AccVGPR accounting, dynamic shared resource limits and the register granule differ by compiler/document revision. Prefer `llvm-calc-occupancy -mcpu=gfx942` or the toolchain occupancy report over a hand formula.

## Matrix operation and pipeline
- MFMA is issued per **64-lane wavefront**, using VGPR operands and VGPR/AccVGPR accumulators. There is no direct `wgmma` warpgroup mechanism, Hopper DSMEM cluster or TMA engine. Direct-to-LDS buffer-load instructions and software-pipelined global→register→LDS scheduling are available.
- Common dense single-block MFMA forms: FP64 `16x16x4`; FP32 `32x32x2` or `16x16x4`; XF32 `32x32x4` or `16x16x8`; BF16/FP16 `32x32x8` or `16x16x16`; FP8/BF8 and INT8 `32x32x16` or `16x16x32`. Supported suffixes and accumulation types require checking the exact ISA.
- Derived instruction cycles (idealized from peak per-CU rates and tile FLOPs, **not a timing measurement**): FP64 16×16×4 ≈32 cycles; FP32 32×32×2 ≈64 or 16×16×4 ≈32; XF32 32×32×4 ≈32, 16×16×8 ≈16; BF16 32×32×8 ≈32, 16×16×16 ≈16; FP8 32×32×16 ≈32, 16×16×32 ≈16. The actual operation may have issue/dependency constraints, not a simple latency equal to this throughput quotient.
- MFMA instruction results have dependency hazards; interleave independent accumulator groups to avoid stalls and consult the ISA scheduler requirements instead of hardcoding `s_nop` spacing.
- CDNA3 supports structured-sparse MFMA instructions such as `v_smfmac_*` for supported 2:4 representations. Validate the encoded sparsity and output equivalence.
- AMD Matrix Instruction Calculator should be used to derive exact operand lanes and accumulator mapping for custom `v_mfma_*` kernels.

## FP8: **format conversion required**
MI300A `gfx942` uses **FNUZ** encodings `e4m3fnuz` and `e5m2fnuz`; H100 uses **OCP** `e4m3fn` and `e5m2`. FNUZ has no negative zero or infinity; bit `0x80` is NaN. E4M3 FNUZ max finite ≈240 vs OCP E4M3 max finite 448. Exponent bias differs (FNUZ E4M3 bias 8), so interpreting the same normal 8-bit pattern without conversion changes values. Use `torch.float8_e4m3fnuz` when available and supported. Convert payload and scaling factors numerically; never byte-reinterpret weights or caches. Verify numeric tolerances, saturation and accumulation precision on MI300A kernels.

## Unified CPU/GPU memory: reason before copying
- MI300A has physically shared HBM and coherent address infrastructure. This can eliminate physically necessary PCIe CPU↔GPU staging, **but not every copy is redundant**: layouts, allocation APIs, ownership, DMA, HSA permissions, host-side consistency and access pattern can make copies useful/required.
- `hipMalloc` device allocations often give better GPU TLB/page behavior; do not assume `hipMalloc` pointers can be indiscriminately dereferenced by every CPU path. Verify HIP pointer attributes and access semantics.
- System `malloc/new` access from GPU requires the active XNACK/HMM configuration and appropriate kernels; first-touch faults may be costly. Measure 4 KiB page behavior vs huge pages only if permitted by system policy. An LLNL study noted significant TLB penalties with small pages; that single system result is not a universal speedup claim.
- CPU vector work is lower bandwidth than the GPU; do not move bandwidth-dominated tensor loops onto Zen 4 merely because the CPU shares HBM.
- Profile page-fault overhead, memory placement, and joint CPU/GPU activity before changing ownership or introducing async host cooperation.

## XCD locality and concurrency
- One MI300A SPX exposes 6 XCDs. L2 is local to each XCD. Many workloads see round-robin assignment of workgroups across XCDs, but **do not assume that the mapping `physical_XCD = workgroup_id % 6` is guaranteed under every driver/runtime/configuration**.
- If the mapping is confirmed for a specific kernel/config, a candidate logical ID remap is `logical=(pid%X)*floor(G/X)+floor(pid/X)` when `G` divisible by `X`, with `X=6` in SPX or `X=2` in TPX. It makes adjacent IDs in the logical tile map share an XCD under ideal round-robin scheduling. Implement the remainder case without collisions when G%X≠0; benchmark and inspect per-XCD cache hits rather than adopting the trick by default.
- Atomic release/acquire **scope matters** for cross-XCD or inter-GPU producer-consumer algorithms. The original device reference claimed cross-XCD coherence requires device-scope publication; treat this as a synchronization-design warning, and verify memory model, allocation scope, and HIP/LLVM code generation for the actual implementation.
- Do not use GPU partitions as a tuning knob on shared HPC nodes without administrator permission. MI300A partitions differ by driver; available modes may include SPX (1×228 CUs), TPX (3×76 CUs), CPX (6×38 CUs). Official driver documentation has version-dependent mode lists. NPS1 is the documented MI300A memory layout; check what the application actually sees.

## Derived idealizations
- FP64 matrix ridge: 122.6/5.3 = **23.1 FLOP/B**.
- TF32 matrix ridge: 490.3/5.3 = **92.5 FLOP/B**.
- BF16/FP16 matrix ridge: 980.6/5.3 = **185.0 FLOP/B**.
- FP8 matrix ridge: 1961.2/5.3 = **370.0 FLOP/B**.
- Ideal square BF16 GEMM meets ridge around `n≈555` (with the idealized `n/3` relation). Decode BF16 weights need approximately batch 185 to amortize one read to that AI, before other traffic.
- Aggregate LDS ~228×64 KiB = **14.25 MiB**, distributed across CUs. Aggregate VGPR capacity ~228×512 KiB = **114 MiB**, not a shared cache.
- BF16 tile 256×256×32 operand stage = `(256+256)*32*2 = 32 KiB`. Two stages consume all 64 KiB LDS, leaving zero for epilogue/barriers; therefore **two fully staged buffers might not fit in a useful implementation**.
- Ideal occupancy/tile wave quantization unit = 228 CUs *in SPX*; use observed partition CU count rather than 228 when partitioned.

## Optimization playbook
1. Compare stock hipBLASLt/Composable Kernel/AITER/Triton AMD GEMM and attention paths before implementing new kernels. Validate dtype, tile launch configuration and MFMA ISA actual presence.
2. Budget 64 KiB LDS first, then use registers aggressively for reuse and FP32 accumulators, balancing VGPR pressure against wave occupancy. Software pipeline global loads into LDS and overlap with independent MFMA groups.
3. For small or ragged shapes, compare 16×16 instruction paths with 32×32 for throughput, waste and instruction count.
4. For repeated reads across adjacent CTAs, test XCD-aware tile mapping and inspect actual per-XCD reuse; never assume MI300X published wins transfer unchanged to MI300A.
5. For CPU/GPU co-design, experiment with shared HBM placement and minimize avoidable allocations or data conversions, but verify host/GPU cache synchronization and end-to-end step time.
6. In distributed ML on four-APU nodes, collect per-rank traces and RCCL transport information, and calculate **exposed** collective delays. Do not equate RCCL kernel sum with lost step time.
7. Run unprofiled paired A/B after every single optimization, with model correctness and training-trajectory checks.

## On-device verification (non-invasive)
```bash
rocminfo
amd-smi list
amd-smi static
amd-smi metric
rocm-smi --showtopo   # only if installed
hipcc --version
rocprofv3 --version
rocprof-compute --version
llvm-calc-occupancy -mcpu=gfx942 --help  # arguments depend on installed LLVM
```
Query `hipGetDeviceProperties()` fields `gcnArchName`, CU count, warpSize, LDS and L2 (if exposed). For partition modes, `amd-smi partition --accelerator` is informational with version-specific flags; avoid `amd-smi set` commands or `sudo` inside the skill. Verify `HSA_XNACK`, HMM driver support, per-device visible CU counts and Slurm CPU/GPU bindings; `rocminfo` output may be extensive.
