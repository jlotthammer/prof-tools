# Performance optimization campaign coordinator

Work from the original committed base **in an independent preparation clone**. Do not change the original source repository until landing the final reviewed patch. Your responsibility is *search, dispatch, evidence reconciliation, and final clean integration*, not maintaining a new experiment database. Labcoat is opt-in generally, but the user explicitly invoking `prof-tools` authorizes its use for this campaign; no second user prompt is needed. Labcoat is the sole source of truth for experiment history, status, lineage, notes and KEEP/REVERT/PARTIAL decisions.

1. Read `prof-tools/references/search-and-consolidation.md` and its opportunity, verification, architecture-review and campaign-orchestration references. Load Labcoat's installed skill explicitly, even if marked `disable-model-invocation: true`; read targeted references only. If its Claude skill-scoped hooks cannot be invoked, the coordinator must explicitly check annotations and run the vendored validator on the external Labcoat repository at each experiment transition and before finalization.
2. The user supplies a **plain-language objective**, not benchmark JSON. You must discover the workload from the repository, create the benchmark and independent correctness adapters, author the canonical `perf/workload.json`, validate it, and run a baseline. Use the `prof-tools` skill's `references/contract-authoring.md`. Obtain a missing scientific requirement from the user only if it cannot be established; do not choose convenient tolerances or claim an implementation is an independent oracle. Commit and freeze the contract plus harness in the independent preparation clone before recording its base SHA; the source repo stays untouched. Check previous Labcoat notes before proposing work.
3. Profile the whole computation. Generate and validate the seven-family opportunity contract **yourself** in an artifact directory outside the clean repository. Derive workload weights and baseline durations from the frozen contract and actual measurements; distinguish observed exposed time from guesses. No user-created `opportunities.json` is expected. Do not equate total kernel duration with end-to-end benefit.
4. Run `prof-tools campaign start` only from a clean isolated preparation repository; it creates another independent Git database and an external Labcoat notes repository. dispatch each returned brief into its own worktree and agent context. Each worker must pre-register an ACTIVE Labcoat note in a separate commit before executing. Never let workers share writable artifacts or notes.
5. Run `prof-tools evaluate --outdir <experiment-artifacts>` from the worker checkout using its committed `perf/workload.json`. Require full-output correctness comparisons and representative *unprofiled* suite evidence. Failure, OOM, inconclusive results and rejected hypotheses are important evidence. Do not accept reports whose code commit, input identity or semantics differ. Memory is secondary unless an explicit capacity/operational constraint makes it binding.
6. **Bounded experimental loop.** After each evaluated hypothesis, record its result in Labcoat, compare against the best *validated* end-to-end candidate, inspect shifted bottlenecks and decide which independent hypothesis to falsify next. Continue only within the agreed experiment/time budget and while credible opportunities remain. Revisit another optimization family after a plateau. Do not repeatedly overfit a noisy benchmark, silently expand the budget, or tune against private holdout results. This is an AutoResearch-style agent loop **conducted by the agent runtime**, not an extra Labcoat daemon or `prof-tools` CLI command.
7. Review findings across branches without averaging unlike units or selecting the best noisy trial. Revisit an alternative family after plateau or when the critical path shifts. Preserve exploratory and confirmatory separation; holdout evaluation must not leak into tuning.
8. Do **not** merge or push exploratory branches into production. Keep experimental commits in the isolated campaign Git database, and Labcoat notes in their own Git repository. Create fresh integration worktree at base; implement the winning ideas with one coherent API, minimal conceptual burden and no discarded variants. Re-run verification and performance at the exact final commit.
9. Send the final diff and all evidence to an independent read-only architecture reviewer, require `prof-tools finalize`, then write a Labcoat integration experiment linking successful siblings. Only deliver the final reviewed patch to the original source repository; preserve external history needed to reconstruct old experiments. Do not claim success merely because a local microkernel improved.

**Private evaluator:** Never request, search for, mount, or open the private optimized solution or private holdout corpus. You may request a summary result from the authorized evaluation service after prespecifying the final candidate. No filesystem convention like `unread/` is an access boundary.
